Why SentinelGo

The agent you'd design if you had to trust it with root.

Most endpoint tools ship a heavy stack: a kernel module here, a scripting runtime there, a different installer per OS. SentinelGo goes the other way: one small, auditable, static binary that does its job and gets out of the way.

One static binary per platform

Every build is CGO_ENABLED=0, so there are no shared libraries, no interpreter and no kernel driver. A CI gate rejects any change that adds cgo. All targets cross-compile from one machine.

windows-amd64.exedarwin-arm64darwin-amd64linux-amd64linux-arm64

Updates itself, safely

The agent finds its next release through the backend, then checks the SHA-256 and Ed25519 signature. It replaces itself atomically and rolls back if the swap fails. It refuses unsigned updates.

Ed25519signed releases

A real OS service

Runs as a Windows Service, systemd unit or launchd daemon. It survives reboots, restarts on failure and shuts down gracefully.

Nothing gets dropped

Audit logs are checkpointed and queued on disk, then delivered at least once. Payloads survive outages and reboots, and retries are de-duplicated.

Private by default

No credential material is collected. Credential-like and PII patterns are redacted from task output before upload, and the agent only talks HTTPS.

How it works

Facts flow up. Signed actions flow down.

The agent authenticates, reports, streams and keeps itself current, with no hand-holding after install.

  1. EndpointSentinelGo agent · Win · macOS · Linux
  2. heartbeat · inventory · logs ↓   ↑ signed tasks · updates
  3. Backendauth · queue · storage · release distribution
  4. risk · compliance · alerts ↓   ↑ policies · commands
  5. Consoleadmins · helpdesk · employee portal

Authenticate

Each agent signs in with its own identity and receives short-lived tokens, renewed in the background. A rejected session recovers once, automatically.

Report

A heartbeat every few minutes (default 5) plus periodic full hardware, software and posture inventory, with fast first sync after enrollment.

Act

The agent polls for tasks, fetches and verifies any installer files, runs the task with timeouts, and returns structured results.

Stay current

It checks for signed releases for its platform and architecture, verifies them, swaps itself atomically and restarts cleanly.

Supply-chain trust

Verifiable from commit to device.

An agent that runs with elevated privileges on every machine has to earn trust. Every release follows the same chain, and every link can be checked independently.

Decisions, in the open

What we build next, and what we won't.

A roadmap is only as good as the things it says no to. Both of these decisions are written up in full on the project wiki.

● Building next

Native MDM for macOS

On Windows and Linux, an agent running as SYSTEM/root can enforce policy itself. macOS routes that authority through Apple's MDM protocol, so we're adding it to the backend we already run.

● Deferred

Most of DLP's real-world value comes cheap: USB control, encryption and posture, which are already on the roadmap. Real-time content blocking needs kernel drivers on Windows and macOS. That cost is high and the return is low.

Get started

Verify, install, done.

Every device installs from a device bundle downloaded from your console. It holds the agent, a config.json with that device's credentials, the installers and SHA256SUMS. The installer puts the agent in place, installs the config and starts the service.

  1. Download the bundle

    In the console, open the agent download, pick the OS and CPU architecture, and unzip the bundle on the device.

  2. Verify it

    Check every file against SHA256SUMS. The installers also verify the agent binary themselves, and refuse to run without the checksum file.

  3. Run the installer

    Use the terminal steps below, or double-click install.command (macOS), install.bat (Windows) or sentinelgo-install.desktop (Linux).

# In the unzipped device bundle
$ sha256sum -c SHA256SUMS --ignore-missing

# Installs to /opt/sentinelgo, adds config.json, starts systemd
$ chmod +x install.sh
$ sudo ./install.sh

# Confirm the service is running
$ sudo ./install.sh status
# In the unzipped device bundle
$ shasum -a 256 -c SHA256SUMS --ignore-missing

# Picks the right binary for this Mac, installs to
# /opt/sentinelgo, adds config.json, loads launchd
$ chmod +x install.sh
$ sudo ./install.sh

# Confirm the service is running
$ sudo ./install.sh status
# In the unzipped device bundle; compare each hash
# with its line in SHA256SUMS
PS> Get-FileHash .\install.bat -Algorithm SHA256
PS> Get-FileHash .\sentinelgo-windows-amd64.exe -Algorithm SHA256

# From an elevated prompt (or double-click: it asks
# for admin rights). Installs the agent and config.json
# and starts the Windows Service.
PS> .\install.bat

FAQ

Questions, answered straight.

Is SentinelGo an MDM?

Today it is agent-based endpoint management: inventory, posture, CVEs, compliance, policies, workflows, software deployment and remote actions on Windows, macOS and Linux. On Windows and Linux the agent can apply settings directly.

Native Apple MDM is on the roadmap as the next major step, because macOS only allows certain controls (configuration profiles, privacy grants, FileVault escrow) through MDM.

Does it install a kernel driver or system extension?

No. The agent is a user-space service written in pure Go with cgo disabled. That's a deliberate rule enforced in CI: it keeps the binary static, cross-compilable and free of the crash risk that comes with kernel code.

What data does the agent collect?

Hardware and software inventory, OS services, network configuration, security posture and OS audit logs. It does not collect credential material, and it redacts credential-like and PII patterns from task output before upload.

Run -debug-dump to print everything the agent would send, with nothing uploaded.

How are updates kept safe?

Releases are built reproducibly, signed with Ed25519, listed in SHA256SUMS, and shipped with provenance attestations and an SBOM. The agent verifies the signature and checksum before an atomic swap, and refuses unsigned binaries.

Which platforms are supported?

Windows (amd64), macOS (Apple silicon and Intel) and Linux (amd64 and arm64), running as a Windows Service, launchd daemon or systemd unit.

How do I report a security issue?

Please report it privately through the security policy, not as a public issue.
